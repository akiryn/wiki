# Fontconfig
**Fontconfig 是 Linux 上负责发现和匹配字体的库。** 应用告诉它想用什么字体，比如 `Adwaita Sans`，Fontconfig 会从系统和用户安装的字体中找出合适的字体文件。它还支持别名和回退规则，比如把通用名称 `sans-serif` 匹配到具体字体，或为主字体缺少的中文字符提供候选字体。

`monospace` 是一个**通用字体名**。运行 `fc-match monospace`，实际匹配到的可能是 `Noto Sans Mono`。同类通用名称还有 `sans-serif` 和 `serif`。


## fc-list
`fc-list` 是 Fontconfig 提供的命令行工具，用于列出系统中可用的字体及其属性。
```
fc-list [选项] [模式] [格式]
```

```bash
fc-list : family | sort -u
```
这里的：
```
: family
```

可以拆成两部分：

- `:`：指定字体匹配模式，这里为空，表示匹配所有字体。
- `family`：指定输出字体的 family 属性。

## fc-match
匹配字体

| 命令                                 | 用途                          |
| ---------------------------------- | --------------------------- |
| `fc-match 'Adwaita Sans'`          | 查看请求 Adwaita Sans 时，首选的实际字体 |
| `fc-match 'sans-serif:lang=zh-cn'` | 查看简体中文无衬线字体的匹配结果            |
| `fc-match -s 'Adwaita Sans'`       | 查看按匹配顺序排列的候选字体              |

# 函数命名方式

驼峰命名法:大驼峰 (UpperCamelCase / PascalCase): 所有单词首字母均大写
蛇形命名法:全小写蛇形 (lower_snake_case)单词间用下划线连接。
匈牙利命名法简化：即在变量名前加上类型前缀，这有助于在调试时一眼看出变量的位宽。

模块前缀命名法：由于 C 语言没有命名空间（Namespace），为了避免冲突，通常在函数和全局变量前加上模块缩写。
    宏定义： 一律大写 UPPER_SNAKE_CASE。
    底层驱动： 常用 module_function_name (全小写蛇形)。
    变量： 常用 p_u8Buffer (前缀 + 驼峰/蛇形)。
    接口函数： 常用 Module_FunctionName (模块名 + 大驼峰)。

## 方向键、粘贴和字符范围

这些行显示的是终端发送的完整编码或 Zsh 的字符范围规则。看到同一方向键列出两套编码，是因为终端在不同键盘模式下可以发出不同的序列。

| 编码 | 对应输入 | 动作与作用 |
| --- | --- | --- |

# MSYS，MSYS2

Minimal GNU(POSIX) SYStem on Window 2 是一个小型的GNU环境的子系统，可以看作Cygwin的升级迷你版

安装后能看到提供了一下五个入口

| 入口           | 默认编译工具链 | 目标平台      | 运行库                | 用途                              |
| -------------- | -------------- | ------------- | --------------------- | --------------------------------- |
| **UCRT64**     | GCC            | Windows x64   | UCRT + libstdc++      | 通用 Windows C/C++ 开发，默认推荐 |
| **CLANG64**    | Clang / LLVM   | Windows x64   | UCRT + libc++         | 使用 Clang、LLVM、LLD 的开发      |
| **MINGW64**    | GCC            | Windows x64   | 旧 MSVCRT + libstdc++ | 维护旧环境；官方已标记弃用        |
| **CLANGARM64** | Clang / LLVM   | Windows ARM64 | UCRT + libc++         | ARM64 Windows 开发                |
| **MSYS**       | GCC（安装后）  | MSYS 兼容环境 | Cygwin 衍生运行库     | Bash、Unix 工具及 MSYS 自身软件   |

它们共享同一个 MSYS2 安装、Bash、基础命令和 pacman，但分别设置：

- **工具搜索路径**：决定优先使用哪个编译器、链接器、CMake 等。
- **库和头文件路径**：使用对应环境的依赖。
- **运行库和 C++ 标准库**：例如 UCRT、MSVCRT、libstdc++、libc++。
- **目标架构**：例如 x64 或 ARM64。

主要用 **UCRT64、CLANG64、MSYS（这个其实也不常用）**

| 环境        | 什么时候用                                           | 对你的建议                           |
| ----------- | ---------------------------------------------------- | ------------------------------------ |
| **UCRT64**  | GCC 编译 Windows C/C++ 程序，使用配套原生库          | **作为默认环境**                     |
| **CLANG64** | 使用 Clang、LLVM、LLD，或搭配 Rust `windows-gnullvm` | 确定走 LLVM 路线时用                 |
| **MSYS**    | 运行 Bash、Unix 工具，维护 MSYS 环境                 | 偶尔用；普通命令在前两个环境也能运行 |

# LLVM

`开源编译器与工具链技术集合`，也是一个项目，是继GNU项目后新发起的一个大项目

***\*Clang\**** 是一种开源的编译器前端，是LLVM项目的一部分，主要用于编译 **C、C++、Objective-C 和 Objective-C++** 等编程语言。它通常与 **LLVM** 后端配合使用，旨在成为 GNU 编译器套装（GCC）的现代化替代品。

## Clang相关

Clang 属于LLVM项目，但Clang同样可以和GNU项目的工具混搭使用，见下方解释

**编译器的前端（如 Clang）只负责把代码翻译成机器码（生成 `.obj` 目标文件），但要变成最终能在Windows运行的 `.exe` 程序，还必须依赖操作系统的头文件、C/C++ 标准库以及链接器。**Windows 本身不自带像 Linux 那样的标准开发环境，因此 Clang 在 Windows 上必须“依附”于现有的**两种生态之一**，注意以下讨论的是 **“在 Windows 原生系统下编译出 Windows 可执行文件（`.exe`）”** 的场景，还有wsl2单独讨论**这种方式是在Windows下编译出linux可执行文件**：

1. MSVC模式（借壳微软原生生态）

   在这种模式下，Clang 彻底融入微软的 Visual Studio 生态。

   - **工作原理**：只使用 Clang 作为编译器核心，但**头文件、C++ 标准库（STL）以及链接器（`link.exe`）全部直接使用微软 MSVC 的组件**。
   - **兼容性（ABI 兼容）**：生成的目标文件（`.obj`）与 MSVC 编译器生成的文件格式完全一致。这意味着你可以用 Clang 编译代码，然后直接链接微软官方用 MSVC 编译出来的第三方库（`.lib` / `.dll`）。
   - **命令行伪装**：为了让习惯 Visual Studio 的构建系统无缝切换，LLVM 官方甚至提供了一个名为 **`clang-cl.exe`** 的程序。它接收与微软原生编译器 `cl.exe` 完全相同的命令行参数（如 `/O2`、`/W4`），但在底层调用 Clang 进行编译。

   安装方式：在这种模式下使用Clang电脑上必须先装有 **Visual Studio**（或者微软单独提供的 *Build Tools for Visual Studio*，里面包含了 Windows SDK 和 MSVC 的头文件/链接器）。然后再去安装Clang前端

   - 直接在 Visual Studio Installer 中勾选（融入 Visual Studio 生态）
   - 从 LLVM 官网独立安装（适合配合 VS Code / CMake 使用）

2. MinGW/MSYS2模式（在 Windows 上模拟 Linux 生态）

   MinGW（Minimalist GNU for Windows）和 MSYS2 是在 Windows 上提供类 Unix/Linux 开发环境的工具集。

   - **工作原理**：在这种模式下，Clang 完全脱离微软的 Visual Studio 工具链，转而使用 **开源社区提供的 GNU/LLVM 组件**（如标准库 `libc++` 或 `libstdc++`，链接器使用 LLVM 的 `lld` 或 GNU 的 `ld`），并直接调用 Windows 底层的系统 API（Win32 API）。
   - **独立性**：不需要安装体积庞大的 Visual Studio，所有工具都可以像在 Linux 下用 `apt` 一样，通过 MSYS2 的包管理器（`pacman`）独立安装和更新。
   - **使用习惯**：命令行的参数风格与 Linux/macOS 下的 Clang 完全一致（如 `-O2`、`-Wall`），非常受习惯 Linux 开发环境、使用 CMake 或 Makefile 构建开源项目的开发者欢迎。

   安装方式：

   - 下载免安装的独立打包版 GitHub 搜索 **`llvm-mingw`**
   - 通过 MSYS2 安装打开 **`MSYS2 CLANG64`** 终端`pacman -S --needed base-devel mingw-w64-clang-x86_64-toolchain`安装的是完整的纯血 LLVM/Clang 工具链。底层使用 LLVM 自家的 C++ 标准库（libc++）和链接器（lld）。整个工具链完全不依赖任何 GCC 组件，编译链接速度最快、最新特性支持最激进。
   - 通过 MSYS2 安装打开 **`MSYS2 UCRT64`** 终端`pacman -S mingw-w64-ucrt-x86_64-clang`安装的是GCC 主场，混搭 Clang。在 UCRT64 里安装 Clang，它会被配置为借用 GCC 的 C++ 标准库（libstdc++）。唯一使用场景是项目既需要用 GCC 编译一部分代码，又需要用 Clang 编译另一部分代码，且两者必须互相链接（要求 C++ 标准库二进制 ABI 兼容）时。

我选择MSYS2CLANG64+Clang Toolchains全家桶、MSVC+LLVM 官网独立安装clang+llvm-xxx-pc-windows-msvc.tar.xz+Build Tools for Visual Studio。此外还有wsl2方式，这种好理解就是当作Linux环境了

Windows 电脑上使用 Clang 的三大流派

如果把视野扩大到“在 Windows 电脑上写 C/C++ 代码”，选择的其实是这三种方案：

| 方案                      | 运行环境             | 最终生成产物           | 最适合的开发场景                                       |
| ------------------------- | -------------------- | ---------------------- | ------------------------------------------------------ |
| **1. MSVC 模式**          | Windows 原生         | Windows `.exe`         | 开发纯 Windows 桌面软件、游戏、依赖微软生态的商业项目  |
| **2. MinGW / MSYS2 模式** | Windows 原生         | Windows `.exe`         | 跨平台开源项目本地调试、日常 C/C++ 学习、算法刷题      |
| **3. WSL2 模式**          | 虚拟机中的真实 Linux | Linux 二进制文件 (ELF) | 后端服务器开发、Linux 驱动/系统编程、纯 Linux 开源项目 |

# Rust

## Windows平台下

**Rust 编译器（`rustc`）的后端同样基于 LLVM**，**rustc**也只负责把 Rust 代码翻译成机器码；要在 Windows 上生成最终的 `.exe`，它依然需要“借壳”附着在 **MSVC** 或 **MinGW/GNU** 这两套生态之一上。

- x86_64-pc-windows-msvc（官方默认推荐，对应 MSVC 模式）借用微软的 **Visual Studio C++ 构建工具**（提供 Windows SDK 头文件和 `link.exe` 链接器）Rust 官方在 Windows 上的首选默认配置，生态兼容性最好。
- x86_64-pc-windows-gnu（对应 MinGW / MSYS2 模式）借用开源的 MinGW-w64 工具链（提供 GNU 链接器 ld 和 Windows API 头文件）。体积轻巧，但是少数重度依赖微软原生库的 Rust 第三方包可能会编译报错。这种方式是直接安装在Windows系统上的且 Rust 官方为了让你不用单独去下载安装 MSYS2 或配置环境变量，直接在 x86_64-pc-windows-gnu 这个工具链里内置了一个精简版的 MinGW-w64（包含了 gcc.exe 驱动、ld.exe 链接器和必要的 Windows API 头文件）。安装完成后在powershell开箱即用
- x86_64-pc-windows-gnullvm类似x86_64-pc-windows-gnu

MSYS2 的软件仓库里，同样按照子环境提供了预编译好的 Rust 包但都不推荐(我不使用MSYS2参与Rust环境的搭建)

```bash
pacman -S mingw-w64-ucrt-x86_64-rust
pacman -S mingw-w64-clang-x86_64-rust
```

原因主要有三个，核心在于 **Rust 自身生态已经足够强大，不需要 MSYS2 来当“大管家”**：

| 对比维度           | 官方 `rustup-init.exe`（强烈推荐）                           | MSYS2 `pacman` 安装（不推荐）                                |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **包管理与依赖**   | Rust 自带的 **`Cargo`** 本身就是极其强大的包管理器，直接从官网 `crates.io` 拉取源码编译，完全不依赖系统的包管理器。 | 用 `pacman` 装 Rust 属于“多此一举”，破坏了 Rust 官方统一的工具链管理方式。 |
| **版本更新与切换** | 支持用一条命令（`rustup update`）随时升级到最新版，或无缝切换 `stable` / `nightly` 测试版。 | 版本完全受限于 MSYS2 仓库维护者的打包进度，无法使用 `rustup` 灵活切换版本或添加交叉编译目标。 |
| **IDE 兼容性**     | VS Code（`rust-analyzer`）和 RustRover 原生直接识别 `rustup` 路径，开箱即用。 | 安装在 `C:\msys64\ucrt64\bin` 下，很多 IDE 无法自动识别标准库源码路径，配置起来非常繁琐。 |

只有当你的 Rust 项目**必须调用极其复杂的外部 C/C++ 系统级库**（比如在 Windows 上编译依赖 GTK4、GStreamer 音视频框架或 FFmpeg 的 Rust 桌面软件），且你想直接白嫖 MSYS2 仓库里现成的 C 语言动态库时，才会在 MSYS2 终端里通过 `pacman` 安装 Rust 以确保链接环境完全一致。

### 安装配置

## Windows下的wsl2
另外如果使用wsl2，安装的就是纯正的 Linux 版 Rust `x86_64-unknown-linux-gnu`

在 **WSL2（Windows Subsystem for Linux 2）** 下搭建 Rust 开发环境，实际上**比在 Windows 原生环境下更简单、更纯粹**，也是目前很多资深 Rust 开发者在 Windows 电脑上的**首选方案**。

- **彻底告别底层工具链纠结**：不需要在 `-msvc`（几 GB 的 Visual Studio）和 `-gnu`（MinGW 兼容性妥协）之间做艰难选择。在 WSL2 的 Ubuntu 里，目标平台是纯粹的 **`x86_64-unknown-linux-gnu`**，这是 Rust 生态支持最原生、性能最优、编译速度最快的环境。

- **第三方依赖零阻力**：Rust 生态中有不少库（如 OpenSSL、SQLite 或各类网络/异步底层库）在编译时需要调用操作系统的 C 库。在 Linux 下只需一条 `sudo apt install build-essential libssl-dev` 就能完美解决，省去了 Windows 下各种环境变量和路径报错的烦恼。

  

  另外在 WSL2 里编译出来的默认是 Linux 程序；如果 WSL2 里写完代码，突然想编一个 `.exe` ，甚至不需要切回 Windows，只需在 WSL2 里装一个交叉编译目标 `rustup target add x86_64-pc-windows-gnu` 就能直接生成 `.exe`。

  

### 安装配置

```bash
sudo apt update && sudo apt install -y build-essential curl
curl --proto '=https' --tlsv1.2 -sSf https://rustup.rs | sh
source "$HOME/.cargo/env"
```

默认安装下来的是`x86_64-unknown-linux-gnu`，要说明没有类似x86_64-unknown-linux-llvm。

这里的 `gnu` 主要表示目标平台采用 GNU ABI／glibc 环境，不是在指定“用 GCC 编译 Rust”。Ubuntu 默认使用 GNU C Library，也就是 **glibc**，因此通常对应 `x86_64-unknown-linux-gnu`。

```txt

                                  ├→ Clang 驱动 LLD → Linux 程序
C/C++ 源码  → GCC /Clang + LLVM ──┘
```

# POSIX

**Portable Operating System Interface** ，可移植操作系统接口

就是一套让一堆操作系统去遵循的规范，操作系统遵循这个规范后，在操作系统之上的应用、工具集就很方便在不同系统之间移植，降低开发、维护、移植成本。核心规则如下

- **编程接口（API）**：规定文件操作、进程管理、线程同步（如 Pthreads）、信号处理和网络通信等接口规范。
- **Shell 与命令行工具**：规范命令行解释器和常用工具的行为与接口。
- **只定接口，不限实现**：规定函数名、参数和行为规则，具体实现由各系统或库（如 glibc）完成。

Windows系统是不遵循这类规范的。

这类规范是大部分类unix系统遵守的，posix最后的x就是unix。例如macos，linux

Windows上又设计了专门的POSIX子系统(早期为了应付美国国防部的采购标准，当时规定计算机系统必须具备 POSIX 兼容性才能进入联邦采购名单)。其中早期比较流行的就有Cygwin

# Python环境管理发展

python一直分为两大阵营：**跨语言 / 科学计算阵营 (Conda 生态)**，**纯 Python 阵营 (PyPI 生态)**

- **PyPI / Python 打包生态**：以 Python 包的发布、解析与安装为核心。典型工具有 pip、pip-tools、pipx、Poetry、PDM、uv。
- **Conda 生态**：以跨语言包、二进制依赖、Python 解释器及环境管理为特色。典型工具有 conda、mamba、micromamba、pixi。
- 当然它们不是严格隔离的阵营：Conda 环境中可以使用 pip 安装 PyPI 包；pixi 也支持在项目中声明 PyPI 依赖。不过还是建议使用对应的工具。

| 维度         | PyPI / Python 打包生态                               | Conda 生态                                      |
| ------------ | ---------------------------------------------------- | ----------------------------------------------- |
| 常见来源     | PyPI 或其他兼容的 Python 包索引                      | conda-forge、defaults 等 channel                |
| 主要包格式   | wheel（`.whl`）、源码发行包（sdist）                 | `.conda`、`.tar.bz2`                            |
| 依赖范围     | 以 Python 项目及其依赖为中心，wheel 也可携带原生代码 | Python、R、C/C++ 库、编译器和系统级二进制依赖等 |
| 环境管理     | venv、virtualenv、uv 等                              | conda、mamba、micromamba、pixi                  |
| 常见项目工具 | pip、Poetry、PDM、uv                                 | conda、mamba、pixi                              |

有如下几个大类：包管理工具（pip，Poetry，PDM，uv，conda，mamba，pixi），虚拟环境工具（virtualenv，venv），Python版本管理工具（Pyenv）

## 纯python生态(PyPI 生态)

pypi是一个python包托管平台，由PyPA组织维护(一个维护 Python 打包相关项目的小组)，使用pip，uv，poetry等pypi生态的包管理工具下载包都是从pypi这个仓库下载包

pip是Python包安装核心引擎，最基本也是最广泛使用的 Python 包安装工具，

requirements.txt用于描述依赖文件，主要回答：这次要安装哪些依赖、遵循什么安装约束？但是该文件手动管理麻烦，自动生成又会被加入很多间接依赖，于是有了pyproject.toml，这是官方提出的统一的配置文件，这是一个什么项目、它声明依赖什么、用什么方式构建？

| pip              | 包管理器                                                     |

| PyPA             | 一个维护pypi的团队                                           |
| pyproject.toml   | 官方提出的统一的配置文件，避免项目中有许多描述工具的配置文件，同时可以替代requirements文件 |

此外还有setuptools该工具构建后端及打包工具，历史悠久。pip-tools工具辅助生成pip要安装的依赖。virtualenv一个第三方虚拟环境工具区别于venv一个标准库虚拟环境工具。pipenv早期项目依赖和虚拟环境管理器。Poetry，PDM更现代一步的管理器。uv更更现代化的管理器(Rye已经合并到该项目中)

pyenv一个Python 解释器版本切换工具，注意区别于上方提到的包管理工具，依赖处理工具

pipx	Python CLI 应用安装工具每个应用使用独立环境，命令通常暴露在用户 PATH 中；不等于系统级安装

## 跨语言 / 科学计算阵营 (Conda 生态)

官方的pip用于安装包但是对NumPy，Pandas，SciPy等一些科学计算领域的包支持不好，于是一家公司打包了一堆这些pip处理不好的包叫做AnacondaDistribution(后来这家公司直接改名叫Anaconda了)，同时目前ai使用的一些cuda等包pip也不好处理也提高了Anaconda热度。

AnacondaDistribution是一个大包，conda是后续添加的管理瘦身这个大包的命令行工具，实际和pip功能一模一样。pip管理的大包可以看作是python官方维护的软件仓库，conda管理的大包是anaconda公司维护的，不过由于anaconda这家公司对包的管理很好故仍和pip共存

conda可以在本地下载依赖管理conda虚拟环境在远程又一个软件仓库，就是一个完整且独立于python的软件生态。几乎和pip，python软甲库等一一对应

使用conda管理环境的话就不能使用pip了

| 名词                 | 含义                                                         |
| -------------------- | ------------------------------------------------------------ |
| AnacondaDistribution | 一个包罗万象的包由，Anaconda公司提供                         |
| Conda                | 用于管理AnacondaDistribution，添加更新这里面的包             |
| miniconda            | 由于Conda可以管理Anaconda环境所以就不需要一个大包了，MINICONDA就是一个只包含conda管理器的极小包 |



官方为了拓展AnacondaDistribution这个包，提供更多软件但又担心兼容性于是开发了一个平台anaconda.org，官方将原来AnacondaDistribution中内容拆为 main，R，msys2 三个集合每个集合称为一个channel，这三个总和称为defaults 也是conda的默认下载源。普通用户都可以上传并维护自己的channel，开源社区维护了一个channel叫做conda-forge目前是最大的channel且已有取代官方包趋势，后来官方维护的channel开始收费，用户开始转向conda-forge这个channel下载包，但是conda这个工具默认指向官方的channel，虽然可以添加命令行参数或修改配置文件指向forge但是麻烦于是社区开发了miniforge对标miniconda，就只重新开发conda将其默认channel指向了conda-forge这个channel。

anaconda收费的是channel里面的软件包，不让下载这个channel，但是conda这个工具是开源的，所以才有miniforge出现。

mamba解决conda不够快的问题，pixi解决conda不够现代的问题， Conda 的**底层工作流和设计理念**落后，所有有了pixi。这些都是包管理工具

锁文件与依赖升级

| 命令                                 | 用途                                   |
| ------------------------------------ | -------------------------------------- |
| `uv lock`                            | 解析依赖并更新锁文件，不安装到环境     |
| `uv sync`                            | 根据项目和锁文件同步环境               |
| `uv sync --locked`                   | 要求锁文件已与项目配置一致，否则报错   |
| `uv lock --upgrade`                  | 在项目允许的范围内重新选择较新依赖版本 |
| `uv lock --upgrade-package requests` | 允许指定依赖升级，必要时连带调整其依赖 |
| `uv sync --upgrade`                  | 重新解析升级，并同步到环境             |
